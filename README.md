# ModularBlazor.Module.Taxonomies

Taxonomies: a runtime module of the [ModularBlazor](https://github.com/soft-square-net/ModularBlazor.Platform)
platform, in [Ardalis Clean Architecture](https://github.com/ardalis/CleanArchitecture) layers. It keeps the tenant's
**schemes**: controlled vocabularies such as site sections, product categories or genres, each a tree of **terms**
(one parent per term), written out as a schema.org `DefinedTermSet` of `DefinedTerm`s. A term can stand for a concept
of the Keywords module (by id, with a name snapshot), so content classified with it is about that concept too. Other
modules choose terms with the `pick-terms` dialog.

## Layout

```
src/WebApi.Modules.Taxonomies.Core/             Core: SchemeAggregate (TaxonomyScheme and its Term tree, rules, JSON-LD, search keys) and specifications
src/WebApi.Modules.Taxonomies.UseCases/         use cases: Mediator commands and queries over schemes and terms, returning an Ardalis Result
src/WebApi.Modules.Taxonomies.Infrastructure/   data: TaxonomiesDbContext, entity configurations, tenant migrations per database provider
src/WebApi.Modules.Taxonomies.Web/              entry assembly: IRuntimeModule, the Carter route table, one REPR endpoint class per route
src/openapi/taxonomies.json                     the module's OpenAPI document, exported from Web (see "Building")
src/WebApi.Modules.Taxonomies.Client/           typed API client, generated by NSwag from that document: a hidden client module
src/Module.Taxonomies/                          Blazor client module: the Taxonomies pages (/taxonomies) and the pick-terms dialog
tests/         UnitTests (Core, UseCases; NSubstitute) and IntegrationTests (Infrastructure on SQLite)
playground/    Aspire AppHost: the platform (from a Platform checkout) with this module, see "Developing"
docs/          clean-architecture.md: layers, dependency rules, adding a feature
```

The module's id, route prefix and database schema are `taxonomies`; its permissions are `taxonomies.read` and
`taxonomies.manage`.

## Schemes and terms

A scheme has a unique **key** (`news-sections`; it is the scheme's id in routes and in other modules), a name, an
optional description and a language. Its terms form a tree, at most 8 levels deep and 2000 terms per scheme; a term has
a name, a slug unique in the scheme, an optional code (schema.org `termCode`: an IPTC or internal code; the slug when
empty), a description and an optional Keywords concept. The scheme is one aggregate: every change to it or to its
terms carries the scheme's `version` and answers with the whole scheme, so two editors never overwrite each other (409).
A move never makes a cycle and renumbers the siblings on both sides; only a term without children can be removed, and
only a scheme without terms can be deleted.

| Method and route (under `/api/taxonomies`) | Permission | Use case |
| --- | --- | --- |
| `GET /schemes` | `taxonomies.read` | The schemes, with their term counts |
| `POST /schemes` `{ key, values: { name, description?, language? } }` | `taxonomies.manage` | 201; a key taken is a 409 |
| `GET /schemes/{key}` | `taxonomies.read` | The scheme with its terms in tree order (depth, path, child count) |
| `GET /schemes/{key}/jsonld` | `taxonomies.read` | `{ name, jsonLd }`: the scheme as a `DefinedTermSet` |
| `PUT /schemes/{key}` `{ version, values }` | `taxonomies.manage` | Rename, describe, change the language |
| `DELETE /schemes/{key}?version=` | `taxonomies.manage` | Only an empty scheme |
| `POST /schemes/{key}/terms` `{ version, parentId?, values }` | `taxonomies.manage` | Add a term (last among its siblings) |
| `PUT /schemes/{key}/terms/{termId}` `{ version, values }` | `taxonomies.manage` | Edit a term: name, slug, code, description, `conceptId` and `conceptName` |
| `POST /schemes/{key}/terms/{termId}/move` `{ version, parentId?, position }` | `taxonomies.manage` | Move a term, with its subtree |
| `DELETE /schemes/{key}/terms/{termId}?version=` | `taxonomies.manage` | Remove a term without children |
| `GET /terms?search=&scheme=&limit=` | `taxonomies.read` | Terms whose name, slug, code or concept contains the text (case, accents and Arabic letter forms ignored), in tree order |
| `GET /terms/lookup?ids=1&ids=2` | `taxonomies.read` | The terms with these ids, in the order asked, with their scheme and path |
| `GET /terms/{id}/jsonld` | `taxonomies.read` | `{ name, jsonLd }`: the term as a `DefinedTerm` in its set |

Every call needs a signed-in caller in a tenant (`X-Tenant` header or the token's tenant). The setting
`Taxonomies:MaxPageSize` (default 100) caps the search limit and the ids per lookup; change it on the Host Modules page.

In the Blazor client, the **Taxonomies** menu entry opens the scheme list (`/taxonomies`, with a form for a new scheme)
and the scheme editor (`/taxonomies/scheme?key=`): the tree with up, down, indent and outdent moves, a side panel to
edit a term and choose its concept, the scheme's settings and its JSON-LD. Choosing a concept opens the Keywords
module's `pick-concepts` dialog when that module is installed; without it the editor takes a concept id typed in.

### The pick-terms dialog

Other client modules open it with `IModuleDialogs.ShowAsync("Module.Taxonomies/pick-terms", parameters)` (check
`IsAvailable` first: the module may not be installed). Ids are strings.

```
parameters  { multiple?: bool, selected?: ["3"], scheme?: "news-sections" }   scheme: only that scheme
result      { ids: ["3"], terms: [{ id, name, path, scheme, conceptId }] }    in the order chosen; nothing when cancelled
```

It browses a scheme's tree or searches all of them. Keep the id and the name or path you got: they are a snapshot for
display, the id is the link.

## Building

```bash
dotnet build
```

```bash
dotnet test
```

The platform packages come from the soft-square-net GitHub Packages feed, which needs a token to restore even though
the packages are public: create a personal access token (classic) with `read:packages` and put it in the environment
as `GITHUB_PACKAGES_TOKEN` (`NuGet.Config` reads it). The platform version is pinned once, in `global.json`.

Tools that need the platform's source run from a checkout of
[ModularBlazor.Platform](https://github.com/soft-square-net/ModularBlazor.Platform). Add a migration for every
database provider after a model change:

```powershell
./src/WebApi/scripts/Add-Migration.ps1 -Project <this repo>/src/WebApi.Modules.Taxonomies.Infrastructure -Name <Name> `
    -MigrationsDir Data/Migrations -Namespace soft.square.net.WebApi.Modules.Taxonomies.Infrastructure.Data.Migrations
```

After an endpoint change, export the module's OpenAPI document again (the entry project is `Web`). The next build of
`WebApi.Modules.Taxonomies.Client` regenerates the typed client from it (NSwag); commit both, so client changes show
up in review:

```powershell
./src/WebApi/scripts/Export-ModuleOpenApi.ps1 -Project <this repo>/src/WebApi.Modules.Taxonomies.Web -ModuleId taxonomies `
    -Output <this repo>/src/openapi/taxonomies.json
```

## Installing

The server part is the build output of `WebApi.Modules.Taxonomies.Web` (`bin/<Configuration>/net10.0`: every layer
plus the private Mediator and Ardalis.Result). Zip it and upload it on the client's Host Modules page
(`/host-modules`, as a platform admin), then activate it: the tenant migrations run per tenant, the routes are mapped
under `/api/taxonomies`.

The client parts are two assemblies, uploaded on the client's Client Modules page (`/client-modules`), the API client
first: `soft.square.net.WebApi.Modules.Taxonomies.Client.dll` (hidden; other client modules may depend on it) and
`soft.square.net.Module.Taxonomies.dll` (the Taxonomies pages and the pick-terms dialog). The playground builds all three for you: `playground/out/taxonomies.zip`
and `playground/out/client/`.

## Developing

`playground/` is a small Aspire AppHost: PostgreSQL, the identity service, one WebApi and the Blazor client, with this
module in it. It builds the platform from source, from a
[ModularBlazor.Platform](https://github.com/soft-square-net/ModularBlazor.Platform) checkout next to this repo:

```
<workspace>/Platform               git clone https://github.com/soft-square-net/ModularBlazor.Platform Platform
<workspace>/Module.Taxonomies      this repo
```

(another location: `--property:PlatformRoot=<path>/`). It uses the platform lab's ports (identity 5090, API 5080,
client 5070), so stop the lab and any other playground first.

```bash
dotnet run --project playground --launch-profile dev
```

| Profile | What it does |
| --- | --- |
| `dev` (default) | The WebApi loads the module straight from `src/WebApi.Modules.Taxonomies.Web/bin/<Configuration>/net10.0` (`Modules:Local`), and the client parts from their build output (`ClientModules:Local`), Development only: installed and active on start. Change code, rebuild, restart the `webapi` resource in the dashboard |
| `install` | The platform starts without the module, as in production; upload `playground/out/taxonomies.zip` on http://localhost:5070/host-modules (sign in as the dev platform admin) and activate it, then the two dlls in `playground/out/client/` on http://localhost:5070/client-modules, the API client first |

In Development the platform seeds the tenants `acme` and `globex`. The playground grants the module's permissions in
`acme` to the dev accounts through `Access:DevGrants`: `acme-admin@modular.local` gets `taxonomies.*`,
`editor@modular.local` gets `taxonomies.read`. Their passwords are in the platform's
`WebApi.Identity.Server/appsettings.Development.json`. Sign in on http://localhost:5070 as `acme-admin@modular.local`
and open **Taxonomies**; the API is browsable at http://localhost:5080/scalar.

To try terms with concepts, load the Keywords module beside this one (dev profile only): build a
[Module.Keywords](https://github.com/soft-square-net/ModularBlazor.Module.Keywords) checkout (`dotnet build`, Debug)
next to this repo, or point at one with `Playground:Keywords`:

```bash
dotnet run --project playground --launch-profile dev -- --Playground:Keywords=<path>/Module.Keywords
```

The playground then loads its server and client parts too and grants `keywords.*` to `acme-admin` and
`keywords.read` to `editor`. `Access:DevGrants` and `ClientModules:Local` need a platform with them (the current
`main`); on an older one, grant the permissions on the Access page and upload the client dlls on the Client Modules
page by hand.

Data stays in the Docker volume `taxonomies-playground-data` and in `playground/.data`; delete both to start over.
